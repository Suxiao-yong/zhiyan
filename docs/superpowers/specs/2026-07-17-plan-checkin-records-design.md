# 学习计划打卡式记录设计

## 目标

把学习记录的主要入口从用户自由填写改为基于既有学习计划的任务打卡，同时保留自由记录，用于临时学习和历史补记。

完成改造后，计划任务与真实学习行为建立明确关联。一个计划任务可以产生多条学习记录，计划实际时长等于这些记录的累计时长；用户必须通过打卡完成任务，不能再单独勾选计划状态制造没有记录的“已完成”任务。

## 现状

项目使用 Vue 3、TypeScript、Pinia、Element Plus、Tauri 2 和 SQLite。前端遵循页面、Store、Service、数据库工具四层结构。

当前存在两条互不关联的数据流：

- `study_plans` 保存计划任务、计划时长、实际时长和执行状态。
- `study_records` 保存用户主动填写的学习时长、做题情况、掌握程度、时段、心情和错题关联。

`study_records` 没有计划外键。仪表盘和计划页面可以直接把计划标记为完成；该操作会在缺少实际时长时复制计划时长，却不会生成学习记录。因此计划完成率、实际学习统计和历史记录可能互相矛盾。

## 方案选择

采用“可空计划外键 + 一对多打卡记录”方案：

- `study_records.plan_id` 关联来源计划。
- 计划打卡记录必须包含 `plan_id`。
- 自由记录的 `plan_id` 为 `NULL`。
- 一个计划允许多次打卡，各次记录分别保存真实学习数据。
- 现有分析、可视化和错题功能继续读取 `study_records`。

不采用按日期、科目和知识点推断关联的方案，因为同一天可能有多个相似任务。也不合并计划表和记录表，因为自由学习、多时段学习和错题明细需要独立的行为记录。

## 数据模型

数据库迁移新增：

```sql
ALTER TABLE study_records ADD COLUMN plan_id TEXT REFERENCES study_plans(id) ON DELETE SET NULL;
CREATE INDEX IF NOT EXISTS idx_records_plan ON study_records(plan_id);
```

TypeScript 的 `StudyRecord`、`RecordInput`、数据库列白名单以及导入导出结构同步增加 `plan_id`。

旧学习记录保持 `plan_id = NULL`，按自由记录展示。旧备份没有该字段时仍能导入。删除计划时，SQLite 和应用层兜底逻辑都会把关联记录的 `plan_id` 置空，历史记录和错题不会丢失。

`study_plans.actual_duration` 继续作为列表和对比统计使用的汇总字段。每次创建、编辑或删除计划打卡记录后，Service 都重新汇总该计划的关联记录，并更新该字段。已有计划的历史 `actual_duration` 在没有新关联记录时保持原值；计划开始使用新打卡记录后，以关联记录汇总为准。

`actual_tasks` 保存最近一次打卡填写的实际学习内容。没有内容时保留计划任务文本，便于计划对比页面展示。

## 状态规则

- 新计划初始为 `pending`。
- 第一次使用“保存进度”打卡后变为 `in_progress`。
- 用户使用“完成任务”提交后变为 `completed`。
- 已完成任务允许补充记录，状态仍为 `completed`。
- 用户可以把未完成任务标为 `skipped`，也可以恢复为 `pending` 或 `in_progress`；恢复后的状态取决于是否已有打卡记录。
- 删除某计划的全部关联记录后，该计划回到 `pending`，但用户明确标记的 `skipped` 保持不变。
- 删除部分记录后重新累计实际时长。已完成计划只要仍有记录就保持 `completed`。
- 编辑记录不能把它改绑到另一个计划。自由记录也不能通过普通编辑变成计划记录。

计划打卡使用计划自身的日期，不执行凌晨 04:00 业务日期归一化。自由记录继续使用现有规则：实时记录在 00:00 至 03:59 归属前一天，手动补记尊重用户选择的日期。

## Service 边界

新增面向计划打卡的业务方法，页面不能自行组合多次数据库写入：

- `getPlanCheckins(planId)`：读取计划的全部打卡记录。
- `createPlanCheckin(planId, input, finish, wrongs)`：校验计划、写入记录和错题、刷新计划汇总及状态。
- `recalculatePlanProgress(planId)`：按关联记录重算实际时长与实际内容。
- `restorePlan(planId)`：根据关联记录数量把已跳过任务恢复为未开始或进行中。

现有 `createRecord` 继续负责自由记录。`updateRecord` 和 `deleteRecord` 在操作带有 `plan_id` 的记录后调用计划汇总刷新逻辑。

数据库插件没有前端事务 API，因此业务方法按“先保存事实记录，再刷新派生计划数据”的顺序执行。若刷新计划失败，记录仍然存在。下次加载计划任务时执行一次轻量汇总校正，避免用户丢失学习数据，也让派生字段恢复一致。

## 页面设计

### 学习记录页

学习记录页包含三个页签：

1. `计划打卡`：默认页签，展示所选日期的计划任务卡片。
2. `历史记录`：保留记录日历、筛选、分页、编辑和删除。
3. `错题库`：保留现有错题管理。

页面默认选择当前业务日期。用户可以选择过去日期补打卡；未来任务只读。页头保留“自由记录”次要按钮。

任务卡显示科目、知识点、计划内容、计划时长、已记录时长、状态和操作：

- 未开始显示“开始打卡”。
- 进行中显示“继续记录”。
- 已完成显示完成标记和“补充记录”。
- 已跳过显示“恢复任务”。

### 打卡窗口

新增专用计划打卡窗口：

- 锁定日期、科目和知识点。
- 展示计划任务、计划时长和累计实际时长。
- 实际时长必填，默认值为尚未完成的计划时长；计划已完成时默认 30 分钟。
- 学习内容默认使用计划任务，用户可以填写本次实际完成内容。
- 复用现有做题数、正确数、掌握程度、学习时段、心情和错题录入。
- 提供“保存进度”和“完成任务”两个提交按钮。
- 实际时长无需达到计划时长才能完成，完成判断由用户决定。

### 仪表盘与计划页面

仪表盘今日待办取消直接完成复选框，改为“打卡”“继续”“补充”和“恢复”操作，并复用同一个计划打卡窗口。

计划日历、列表和任务详情不再允许直接把状态设为 `completed`。用户通过打卡窗口完成任务；`skipped` 和恢复操作仍可直接执行。

历史记录列表增加来源列：计划记录显示“计划打卡”，自由记录显示“自由记录”。计划记录可以查看对应计划摘要。

## 错误处理

- 打卡前重新查询计划。计划不存在时提示“计划已被删除或重新生成”，不写入记录。
- 已跳过任务打卡前先提示用户恢复任务。
- 未来计划禁止提交，避免提前制造实际数据。
- 正确数不能大于做题数，时长必须大于零，沿用现有校验。
- 保存按钮提交期间禁用，避免重复点击生成重复记录。
- 写入记录成功但计划汇总失败时，提示记录已经保存、计划进度将在刷新后校正；页面重新加载时触发校正。
- 删除计划记录前告知用户计划实际时长和状态会重新计算。

## 数据展示与分析

仪表盘今日时长、连续打卡、本周趋势、科目占比、AI 分析和六类可视化仍以 `study_records` 为事实来源，因此自由记录和计划打卡会统一计入统计。

计划完成率只读取计划状态。计划实际时长来自关联记录累计，计划对比页面无需改变展示口径。

记录日历继续用真实记录标记打卡日，不用计划状态代替学习行为。

## 测试策略

Service 单元测试覆盖：

- 自由记录写入空 `plan_id`。
- 计划打卡继承计划日期、科目和知识点。
- 第一次保存进度把计划改为 `in_progress`。
- 完成提交把计划改为 `completed`。
- 多次打卡累计实际时长。
- 编辑和删除计划记录后重新汇总。
- 删除最后一条计划记录后回到 `pending`。
- 已跳过任务的恢复规则。
- 未来计划和不存在的计划拒绝打卡。
- 旧导入数据缺少 `plan_id` 时通过校验。

组件测试覆盖任务卡的状态按钮、打卡窗口预填值、提交防重复及历史记录来源标签。

完整验证运行单元测试、类型检查、生产构建和 ESLint，并更新 `MANUAL_TEST.md` 的每日使用流程、数据迁移、自由记录和多次打卡场景。

## 非目标

- 不增加计时器、提醒或番茄钟。
- 不自动判断任务是否完成。
- 不尝试把旧自由记录按相似字段自动关联到计划。
- 不重写分析、图表或 AI 计划生成算法。
